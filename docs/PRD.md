## 2. 产品目标

SixBox 是一款本地优先、插件化、跨平台的桌面工具箱。

产品旨在解决以下问题：

- 现有软件无法完全满足个人的特定需求。
- 一些简单功能被包含在臃肿的大型软件中。
- 不同的小工具分散安装，不方便统一管理。
- 用户希望快速开发、安装并长期使用自己的工具。

### 核心原则

1. **轻量化**：按需加载插件，避免无用进程常驻。
2. **插件化**：工具功能与主程序解耦。
3. **本地优先**：基础工具不依赖账号、云端或 AI。
4. **简单易用**：普通用户使用简单，开发者扩展自由。
5. **统一管理**：窗口、后台任务、通知、配置由平台提供公共能力。
6. **渐进扩展**：首版只实现必要功能，不提前建设完整插件市场和商业体系。

## 4. 产品交互架构

SixBox 提供三个主要入口。

### 4.1 主程序管理中心

包含四个一级页面：

| 页面 | 功能 |
|---|---|
| 我的工具 | 查看、搜索、打开已安装工具 |
| 运行中心 | 管理后台服务、查看状态和异常 |
| 插件管理 | 安装、启停、更新、配置、卸载插件 |
| 设置 | 应用设置、快捷键、Node.js、存储、开发者选项 |

主窗口主要负责管理，不强制嵌入插件的工作界面。

### 4.2 全局快捷启动面板

V1.0 必须支持。

- 通过可配置的全局快捷键呼出。
- 默认候选快捷键：`Control + Option + Space`（macOS）。
- 支持搜索已安装工具、插件命令和工具箱内部操作。
- 支持中文、英文、关键词、自定义别名。
- 支持键盘上下选择和 Enter 执行。
- 支持 Esc 清空搜索或关闭面板。
- 执行打开工具命令时，打开或聚焦工具独立窗口。
- 快捷面板隐藏不影响插件后台运行。
- Node.js 不可用时，仍能呼出面板和进入运行时设置。

第一版不提供系统文件搜索、系统应用搜索或 AI 自然语言搜索。

### 4.3 系统托盘

关闭主程序窗口后，工具箱驻留系统托盘。

托盘菜单至少包含：

- 打开 SixBox。
- 打开常用工具。
- 查看后台运行状态。
- 暂停或恢复适用的后台任务。
- 打开设置。
- 完全退出。

完全退出工具箱时，停止所有受管理的插件后台进程。

插件独立托盘图标属于后续扩展能力，不要求第一版完成。

## 5. 插件系统

### 5.1 插件组成

一个插件可以自由组合：

- **UI**：独立工具窗口。
- **Worker**：后台执行逻辑。
- **Command**：可通过快捷面板、界面等入口调用的操作。

不要求所有插件必须拥有窗口或后台 Worker。

### 5.2 插件管理

V1.0 支持：

- 从本地插件包安装。
- 开发者模式加载本地目录。
- 查看插件列表、详情及版本信息。
- 启用和禁用插件。
- 启动、暂停、恢复适用的后台任务。
- 查看插件运行状态与错误日志。
- 卸载插件，并可选择保留配置和业务数据。
- 手动更新插件，避免更新造成配置丢失。

插件安装、禁用、更新和卸载应同步更新快捷面板的命令索引。

### 5.3 插件状态

将状态拆分为三个独立维度：

| 维度 | 状态 |
|---|---|
| 安装 | 未安装、已安装 |
| 启用 | 已启用、已禁用 |
| Worker | 未运行、启动中、运行中、暂停、异常 |

纯 UI 插件没有后台 Worker 是正常情况，不应被误判为停止或异常。

### 5.4 生命周期

- 关闭插件窗口不停止后台 Worker。
- 同一个单实例工具重复打开时，激活已有窗口。
- 禁用插件时关闭其窗口、停止后台任务并注销命令。
- 后台 Worker 异常时尝试有限次数的自动恢复。
- 多次恢复失败后进入异常状态，等待用户处理。
- 完全退出主程序后，停止所有插件后台任务。

## 6. 插件 SDK

V1.0 提供最小 TypeScript SDK，优先实现：

| 模块 | 能力 |
|---|---|
| `app` | 插件身份、版本、运行环境 |
| `windows` | 打开、激活、关闭插件窗口 |
| `commands` | 统一注册和执行命令 |
| `config` | 持久化插件配置 |
| `state` | 发布和订阅运行状态 |
| `notifications` | 系统通知 |
| `logger` | 统一日志 |
| `lifecycle` | Worker 启动、停止和清理 |

插件开发不应要求修改 Rust 宿主。

通用定时调度、剪贴板、文件系统、插件独立托盘图标等扩展 API，后续按实际插件需求增加。

## 7. Node.js Runtime Manager

### V1.0

- Rust 主程序可以在 Node.js 不可用时启动。
- 完整版内置经过验证的 Node.js。
- 启动时检测运行时是否可用。
- 提供运行时版本、路径、来源及健康状态。
- Node 不可用时展示诊断和恢复入口。
- 管理服务异常不得无条件导致整个桌面宿主退出。

### 后续版本

- 支持系统 Node.js 检测。
- 支持手动指定 Node.js。
- 支持自动下载安装运行时。
- 支持运行时切换、更新和失败回滚。
- 构建完整版 Full 与精简版 Lite。

两个发行版本保持相同产品功能，差异主要在于是否随安装包附带 Node.js。

## 8. 数据存储

采用系统标准应用目录。

主要数据划分如下：

| 数据 | 目录 |
|---|---|
| 已安装插件 | `plugins/` |
| 插件持久化数据 | `plugin-data/` |
| 主程序设置 | `settings/` |
| 主程序数据库 | `data/` |
| 下载的 Node.js | `runtimes/` |
| 缓存、日志 | 系统标准缓存及日志目录 |

插件程序和用户数据必须分离。

插件更新不应覆盖用户配置。卸载插件时默认保留数据，允许用户明确选择清除。

### 敏感凭据

V1.0 不实现用户密码、Token、API Key 的持久化管理。

未来统一采用平台 SecretStore，优先考虑“本地加密文件 + 主密码”，不强制依赖系统钥匙串。

工具箱内部用于通信的临时认证机制不受此延期影响，必须在 V1.0 正常实现。

## 9. 安全边界

V1.0 只支持自己开发或明确信任的插件。

- 插件 UI 不直接获得完整系统原生权限。
- 通过平台 SDK 限制和校验宿主 API 调用。
- 本地通信需要身份验证、来源检查和访问范围限制。
- 日志默认不记录用户输入的完整业务内容。
- Node Worker 独立进程不被视为恶意代码安全沙箱。
- 暂不提供面向不可信第三方插件的开放市场。

未来正式开放公共插件生态前，需要单独完成可信分发、权限强制执行和安全隔离设计。

## 10. V1.0 验收标准

正式版至少满足：

1. 不依赖系统预装 Node.js，完整版能够正常启动。
2. 没有可用 Node.js 时，仍能打开基础管理与诊断界面。
3. 动态安装插件，不需要重新构建主程序。
4. 插件能打开独立窗口，不影响其他工具使用。
5. 关闭窗口后，后台监控继续正常运行。
6. 后台 Worker 崩溃后能够按策略恢复。
7. 完全退出后，被管理的后台进程正确停止。
8. 插件配置在重启和正常版本更新后保留。
9. 全局快捷面板可以呼出、搜索、打开工具与执行命令。
10. 插件禁用、卸载后，相关窗口、后台任务和命令入口得到清理。
11. 系统托盘的打开、隐藏和退出操作经过实际操作验收。
12. 长时间运行、睡眠唤醒、单实例及配置异常场景经过必要测试。

验收以 macOS Apple Silicon 的正式构建包为基线，不以开发模式成功代替正式包测试。

## 11. 第一批插件

### 网络质量监控

用于验证后台运行、状态同步、系统通知、配置和异常恢复。

首版能力：

- 配置监控目标与检测间隔。
- 检测网络延迟与失败状态。
- 设置异常阈值。
- 提供暂停、恢复和立即检测命令。
- 显示当前状态和基础历史记录。
- 检测异常时提供系统提醒。

### JSON 工具

用于验证即时型工具、独立窗口与动态插件安装。

首版能力：

- JSON 格式化。
- JSON 压缩。
- JSON 格式校验。
- 错误提示和定位。
- 不需要常驻 Worker。

## 12. 暂不进入 V1.0

以下功能不作为首版开发任务：

- Windows、Linux 正式适配。
- Lite 精简版公开分发。
- 插件市场和在线自动更新。
- 第三方商业插件体系。
- MCP 和 DeepSeek Harness 对接。
- 内置 AI 助手。
- Django 云同步。
- 用户账号和收费体系。
- 主密码加密保险库。
- 多语言插件运行时。
- 任意原生 GUI 插件接入。

这些功能不应成为首版架构设计的强制复杂度来源。

## 13. 开发阶段

| 阶段 | 开发内容 |
|---|---|
| M1 | 正式工程、Rust 启动层、Node Runtime Manager 基础、数据目录 |
| M2 | 通用 TypeScript 插件 SDK、安装和生命周期管理 |
| M3 | 独立窗口、主程序四个页面、统一托盘 |
| M4 | Command Registry、全局快捷启动面板 |
| M5 | 网络监控和 JSON 两个真实插件 |
| M6 | 手动安全更新、异常恢复、长期运行及正式包验收 |

各阶段均需要包含必要的自动化测试和回归验证。
